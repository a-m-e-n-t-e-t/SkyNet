# 04. Алгоритм заполнения карточки модели SkyNet (§12.4 + §14, схема v11.0)

> Самая сложная карточка системы: `фантастические данные/модели/<имя>.md`. Шаблон: `шаблоны/шаблон_модели.md`.
> Порядок этапов выстроен по зависимостям: сначала канон и классификация, затем требования, затем компоновка (нужны карточки изделий), в конце паттерны.
> Критичные метрики: F18 (компоновка), F52 (паттерны), F71/F74 (броня), F80 (подсистемы по типу), F87 (canon_realizable); паттерны P022–P035, P043–P050.

## Предусловия

1. Карточка произведения существует (алгоритм 08) — модель обязана ссылаться через `произведения: [work_id]`.
2. Карточки изделий модели существуют (алгоритм 02) — компоновка P028 размещает их ВСЕ.
3. Материалы брони существуют (алгоритм 01) — слои ссылаются на `material_<id>`.

## Этап 1. Канон-идентификация

1. `id: SkyNet-<имя>` (KEBAB-CASE, префикс `SkyNet-`; пример: `SkyNet-T900`).
2. `источник_происхождения`: `фильм|сериал|игра|комикс|HTML-концепция`; `канон_источник`: «название + год»; `произведения: [work_id]`.
3. Метаданные: `статус_реальности`: `canon|canon_realizable (F87)|real`; `доступность: фантастический` (для canon); `источник.тип: канон`.
4. `производитель`: `Скайнет|Legion|Cyberdyne|прочее`; `функции`: `инфильтрация|штурм|охрана|разведка|поддержка|прочее`.

## Этап 2. Классификация — ДВЕ не дублирующие оси (урок v3!)

1. `тип_модели` — enum §11.0 (7): `гуманоидный|воздушный|наземный_гусеничный|наземный_колёсный|водный_надводный|водный_подводный|стационарный`. ЕДИНСТВЕННАЯ ось физического типа; задаёт обязательные подсистемы (F80) и тип брони (F74). «ИИ-ядро» — это категория, НЕ тип!
2. `категория` — enum (11): `стандартный|жидкий_металл|ранняя_наземная|воздушный_HK|наземный_HK|водный_HK|ИИ-ядро|гибрид|альтернативный_производитель|GRACE|прочее` — семейство/серия, НЕ повторяет тип.
3. `подтип_модели`: `стандартный|жидкий_металл|прочее` (v9.24 — exempt от подсистем).
4. Проверка: старые карточки с полем `класс` читаются как `тип_модели`; новых карточек с `класс` не создавать.

## Этап 3. Физика канона

`физика_канон`: `масса_kg`, `габариты_mm {l, w, h}`, `рост_mm` (для гуманоидов), `примечание`. Данные канона; источники — в «Источниках» тела. Не выдумывать: нет в каноне → `null` (обоснование в примечании).

## Этап 4. Условные блоки (проверить применимость ДО заполнения)

| Условие | Обязательный блок |
|---|---|
| `функции` содержат `инфильтрация` | `маскировка_инфильтратора` (P023) |
| Энергобюджет с RTG/микрореактором | `защита_от_собственной_радиации` (P025) |
| Энергоёмкая модель | `тепловая_карта` в компоновке |
| Боевая модель | `анализ_попаданий` в компоновке |

## Этап 5. Многослойная броня (F71/F74)

1. ≥3 слоя; каждый: `номер`, `материал` (СУЩЕСТВУЮЩАЯ карточка!), `толщина_mm {min, target}` (требование — диапазон разрешён).
2. `тип_брони` по `тип_модели`: `humanoid_light|aerial_ultralight|ground_heavy|naval|stationary_max`; `соответствует_типу_модели: true` (F74).
3. Масса брони ≤ 30% массы модели — проверить и описать в теле, за счёт чего выполняется лимит.

## Этап 6. Требования выживаемости (P022, 7 блоков)

`эми_защита` (уровень hardened|industrial|consumer; порог импульса; экранирование; стандарты), `антибаллистическая_защита` (класс защиты; поражающие средства; эквивалент RHA), `антивибрационная_защита` (диапазон Гц; ослабление dB; тип изоляции), `защита_от_протечек` (жидкости; IP-класс; сварные швы; уплотнения), `оптимум_прочности_каркаса` (текучесть/прочность/усталость/вязкость/модуль; оптимизация критериев), `срок_службы` (целевой 120 лет; деградация; усталостный ресурс; радиационная стойкость), `энергобюджет_120_лет`.

ПРАВИЛО ДИАПАЗОНОВ: в блоках ТРЕБОВАНИЙ конструкция `{min, target}` РАЗРЕШЕНА (спецификация «не хуже min, цель target»). Инвариант PATTERN_03: `выработка_через_120_лет_W ≥ пиковое_потребление_W` (+ `резервирование_источников: true`, `запас_по_мощности`).

## Этап 7. ТТХ (P024) и ЭМС (P027)

- `тактико_технические_характеристики`: мобильность (скорость, разгон, препятствия, грузоподъёмность, автономность), боевые_параметры (реакция, дальности, точность), вычислительные (inference, сенсоры, цели), автономность_без_сети (fallback-режим, кэш тактики).
- `эмс_внутренняя`: изолированные зоны (силовая/вычислительная/сенсоры/связь), разделение питания, изоляция собственного оружия (удаление EMP-источника от электроники).

## Этап 8. Компоновка изделий (P028, F18 — ОБЯЗАТЕЛЬНО)

1. `система_координат` + `начало_координат` + `оси` + `единицы: mm`.
2. `центр_масс`: координата, метод расчёта (сумма mass×coord | CAD_FEM | измерение), допустимое отклонение; `моменты_инерции` Ixx (крен) / Iyy (тангаж) / Izz (рыскание) + метод.
3. `размещения` — ДЛЯ ВСЕХ изделий модели: `id_изделия`, `подсистема`, `позиция_mm {x,y,z}`, `ориентация_град {roll,pitch,yaw}`, `габариты_mm`, `масса_kg`, `зона_модели` (голова|торс_передний|торс_задний|рука_левая|рука_правая|нога|крыло|фюзеляж|прочее), `охлаждение_через` / `защита_через` / `виброизоляция_через` / `подключения_питания` / `подключения_данных` (через какие изделия).
4. `критические_расстояния` — для моделей с RTG/микрореактором/EMP/лазером: `между` [источник, электроника], `тип_проверки` (P025_радиация | P027_изоляция_оружия | P022_3_вибрация), `минимальное_mm` / `фактическое_mm`, `статус: ok|warning|violation` (violation не допускается).
5. `зоны_защиты` (Faraday cage, био-защита, нейтронная, гамма-экран, броня: имя, тип, материал, толщина, охватывает).
6. `анализ_попаданий` (опц.): зоны уязвимости + критичные изделия + защита минимум. `тепловая_карта` (опц.): источники тепла / охладители / `баланс_тепла: ok|warning|violation`.

## Этап 9. Структурные блоки §12.4.9–§12.4.18

`программное_обеспечение` (Neural Net CPU + SkyNet OS; secure_boot при autonomy > 1 ч — P030); `единая_эми_стратегия` (Standalone/Hive/Rogue — P031); `единая_герметичность` (IP-класс целого; cryo-storage); `сертификация_модели_целого` (тест + канон_верификация); `журнал_экземпляра` (serial, production_date, deployments, kill_count, last_mission); `утилизация_после_120_лет`; `экипаж_оператор` (0 для автономных); `промышленная_база` (P033); `alice_specs` (P034); `original_improved: canon|ии_улучшенный` (P035).

## Этап 10. Операционные паттерны §14 (F52)

Обязательность: `PATTERN_02` (критичность → резервирование), `PATTERN_03` (иерархия деградации), `PATTERN_12` (эшелонированная защита — ≥2 уровня на класс угроз) — ВСЕГДА; `PATTERN_05` (secure boot chain) — при autonomy > 1 ч; `PATTERN_10` (power gating) — для активных моделей; `PATTERN_01` — активные; `PATTERN_09` — стелс/инфильтраторы; прочие — по применимости.

Порядок: сначала `applied_patterns` (список флагов), затем сами блоки:

- `operational_modes` (+ `transitions`): mode_id, power_W, heat_W, active_subsystems, duration, triggers, kpi_per_mode;
- `criticality_classification`: critical_functions (redundancy_type TMR_2_of_3|dual_active|hot_standby|N_voting, voters, vote_rule) + non_critical_functions;
- `degradation_hierarchy`: уровни 100 → 75 → 50 → 25 → 0 (sources, power_W, mode, duration) + `level_zero_behavior` (recovery_trigger, recovery_action);
- далее применённые: `distributed_architecture`, `secure_boot_runtime`, `behavioral_models`, `interaction_vectors`, `self_repair_system`, `signature_budget`, `power_gating` (always_active_minimum + total_always_active_W), `combined_actions`, `defense_layers`, `target_identification`.

## Этап 11. Связи и реализации

- `relations`: `successor_of`, `variation_of`, `hybrid_of`, `paradigm_shift_from` — ссылки на существующие модели.
- `реализация_промышленная` / `реализация_ии` — после создания реализаций (алгоритм 05); обратные ссылки двусторонние.

## Этап 12. Тело и чек-лист

`## Описание` (модель, роль, история; отличие от предшественников — резюме relations), `## Физические параметры (канон)`, `## Многослойная броня` (как работает по слоям, за счёт чего ≤30% массы), `## Произведения, где появляется` (ссылки на work_NNN), `## Реализации`, `## Уязвимости` (канон), `## Связи с другими моделями`, `## Источники`, `## Чек-лист` (из шаблона).

## Этап 13. Самопроверка (ключевое)

- [ ] `expected_subsystems` соответствуют типу модели (F80).
- [ ] Нет дубля осей: физический тип — только `тип_модели`; семейство — `категория` (v3).
- [ ] Броня: ≥3 слоя, ≤30% массы, тип соответствует типу модели (F71/F74).
- [ ] `{min, target}` — только в блоках требований; фактические значения — одиночные числа.
- [ ] Все `размещения` ссылаются на существующие изделия; `критические_расстояния` без violation.
- [ ] Инфильтрация → блок маскировки заполнен (P023).
- [ ] `выработка_через_120_лет_W ≥ пиковое_потребление_W` (PATTERN_03).
- [ ] `произведения` и реализации ссылаются на существующие карточки.
- [ ] Конвенция единиц латиницей: `_kg, _mm, _W, _s, _m, _m2, _GHz, _dB, _pct, _J, _ms`.

## Коммит

`feat(модели): SkyNet-<имя> — <название>`.

## Типичные ошибки ИИ

- Поле `класс` вместо `тип_модели` (дубль осей — урок v3).
- `{min, target}` в фактических значениях (компоновка, физика) вместо блоков требований.
- Броня из несуществующих материалов или <3 слоёв.
- Компоновка покрывает не все изделия модели (F18).
- `критические_расстояния` со статусом violation (недопустимо — пересмотреть компоновку).
- PATTERN_12 с одним уровнем защиты на класс угроз (нужно ≥2).
- Вымышленные канонные данные (масса/рост «по памяти» без источника-произведения).
