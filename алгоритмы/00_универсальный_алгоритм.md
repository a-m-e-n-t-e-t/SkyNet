# 00. Универсальный алгоритм заполнения карточки с помощью ИИ (любой тип)

> Применяется к ЛЮБОЙ карточке базы знаний перед алгоритмом конкретного типа (01–10).
> Алгоритм типа уточняет поля; этот задаёт конвейер: определение → дедупликация → источники → id → заполнение → связи → самопроверка → валидация → списки → коммит.

## Этап 1. Определить тип карточки и домен

| Вопрос | Если «да» | Тип | Домен | Алгоритм |
|---|---|---|---|---|
| Существует в реальности (вещество, процесс, устройство, документ, организация)? | да | `материал` / `технология` / `изделие` / `стандарт` / `исследовательская_группа` | `реальные данные/` | 01–03, 06–07 |
| Материал придуман в произведении? | да | `материал` §12.3a | `фантастические данные/материалы/` | 09 |
| Модель SkyNet из канона? | да | `модель_SkyNet` | `фантастические данные/модели/` | 04 |
| Фильм/сериал/игра/книга/комикс? | да | `произведение` | `фантастические данные/произведения/` | 08 |
| Сборка модели из реальных изделий? | да | `реализация_модели` | `результаты/модели/` | 05 |
| Улучшение существующей реальной карточки? | да | обёртка §12.7 | `работа и и/` | 10 |

Статусы реальности по доменам (строго): `реальные данные/` → `real`; `фантастические данные/` → `canon` или `canon_realizable`; `работа и и/` → `ии-улучшенная`. Реальный материал никогда не попадает в `фантастические данные/` и наоборот.

## Этап 2. Проверить, что карточки ещё нет (дедупликация)

1. Поиск по `id` в списке зоны (`_список_*.md`) и в `_сводный_реестр.md`.
2. Поиск по названию в списках и телах карточек зоны.
3. Для материалов — таблица `ALIASES` в `scripts/sync_materials.py` (19 пар синонимов): ссылка-синоним резолвится в каноническую карточку, дубль не создаётся.
4. Проверить `статус: пустой_шаблон`: если `sync_materials.py` уже создал пустую карточку для этой сущности — заполнять ЕЁ, а не создавать новую.
5. Найдена похожая карточка с другим именем → дополнить существующую, а не плодить дубль (F26).

## Этап 3. Собрать и зафиксировать источники

Тип источника указывается ЧЕСТНО (§12.0) — по нему оценивается доверие к данным:

| Тип | Когда | Обязательно приложить |
|---|---|---|
| `user_input` / `пользовательский_ввод` | данные дал пользователь | — |
| `web_search` / `веб_поиск` | найдено в интернете | `url` + дата проверки |
| `вывод_ИИ` / `вывод_ии` | вычислено/сгенерировано моделью | методику в теле карточки |
| `пользовательский_ввод + веб-поиск` | комбинированный | и то, и другое |
| `канон` | извлечено из произведения (модели) | ссылку на `work_id` |

Правила работы с числами (§22):

- Каждое число — с источником; «phantom»-значения без источника запрещены.
- Число «из памяти ИИ» без проверки → сначала веб-поиск или расчёт, потом внесение.
- Конфликт источников → брать первичный (стандарт, производитель, справочник) и описать конфликт в теле.
- Нет данных → `null` + обоснование (см. «Дисциплина null»).

## Этап 4. Сгенерировать id и имя файла (§15a.1)

| Тип | Префикс / правило | Пример |
|---|---|---|
| материал | `material_` | `material_ptfe` |
| изделие | `izdelie_` | `izdelie_termomoduli_pelte` |
| часть | `часть_<родитель>_` | `часть_<родитель>_<имя>` |
| технология | `tekhnologia_` | `tekhnologia_cvd` |
| модель | `SkyNet-` | `SkyNet-T900` |
| стандарт | `standart_` | `standart_do-254` |
| группа | `group_` | `group_nasa_glenn` |
| произведение | `SkyNet-Work-<NNN>` | `SkyNet-Work-004` |
| реализация | `<модель>-реализация-` | `t900-реализация-пром` |
| обёртка | суффикс `__ii` | `material_ptfe__ii` |

Правила: KEBAB-CASE латиницей (кроме `часть_`); имя файла = `<id>.md` (изделия — папка с `_index.md`); длина 3–80; без символов `/\ : * ? " < > |`; пробелы → `_`.

## Этап 5. Скопировать шаблон в целевую папку

1. Источник: `шаблоны/шаблон_<типа>.md`; целевая папка — по таблице состава в `шаблоны/README.md`.
2. Строка 1 итогового файла — всегда `---` (иначе GitHub не распознаёт front matter и «сливает» его с телом).
3. Внутри Markdown-тела разделитель `---` не используется — разделы только заголовками `##`.
4. Служебные комментарии шаблона удалить или оставить как HTML-комментарий `<!-- ... -->`.

## Этап 6. Заполнить front matter (оптимальный порядок)

Порядок «от классификации к деталям» минимизирует переделки:

1. **`метаданные`** — `версия_схемы` точно как в шаблоне; статусы реальности; доступность; статус; источник; даты. ВАЖНО: блок материала v10.1 отличается от v11.0 (`версия_данных`/`реальность`/`доступность_tlr`/`источник.проверено` против `версия`/`статус_реальности`/`доступность`/`источник.дата`) — не смешивать поля разных версий схемы.
2. **Классификация** — `id`, `тип`, enum-поля (класс/категория/подсистема/подтип/тип_модели...).
3. **Иерархия и связи** — родитель, дочерние_части, предок, произведения, relations.
4. **Свойства** — структурные варианты, параметры режимов, физика, требования.
5. **Ссылки на карточки** — материалы, технологии, стандарты, группы, оборудования.

Каждое enum-поле сверить со списком в шаблоне (§0.2: недопустимое значение = блокировка). Не выдумывать значения вне enum — при сомнении брать ближайшее допустимое, старое значение сохранять в комментарии.

## Этап 7. Заполнить Markdown-тело

- Тело = повествование, ссылки, методики, чек-листы. Числа и enum из front matter в теле НЕ повторяются (F26).
- Разделы — заголовками `##`; плейсхолдеры `<...>` заменены; `TODO/TBD/FIXME/XXX` запрещены (§24.2).
- Внутренние ссылки — относительные Markdown-пути (§15a.3).
- Обязательные разделы тела — по шаблону типа; текст пишется по правилу «одна мысль — один раздел».

## Этап 8. Поддержать двусторонние связи

| Добавил ссылку... | ...проверить обратную |
|---|---|
| материал → группа (F7) | группа → «Связанные материалы и изделия» |
| изделие → материал (B-BOM) | материал → «Применение в изделиях» |
| изделие → технология | технология → упоминание/«Оборудование» |
| модель → произведение | произведение → «Модели SkyNet в произведении» |
| реализация → модель | модель → `реализация_промышленная`/`реализация_ии` |
| карточка X → стандарт | стандарт → «Связанные карточки» |
| обёртка → предок | предок НЕ изменяется (остаётся `real`) |

Обратные ссылки обновляются в ТОМ ЖЕ коммите, что и новая карточка.

## Этап 9. Самопроверка (до валидаторов)

1. Чек-лист шаблона (в конце шаблона).
2. Чек-лист алгоритма типа (01–10).
3. Сверка ключевых F-метрик типа (F5, F7, F8, F62, F71, F74, F80...).
4. Текстовый поиск остатков: `<`, `>`, `TODO`, `TBD`, `FIXME`, `XXX`, `varies`.
5. Сверка дат (`ГГГГ-ММ-ДД`) и единиц в суффиксах полей.

## Этап 10. Валидация скриптами

```bash
python3 scripts/sync_materials.py --check    # пробелы в материалах
python3 scripts/generate_lists.py --check    # отставание списков
python3 scripts/validate_templates.py        # если менялись шаблоны
python3 scripts/pre-commit-hook.py           # карточки развёрнутой базы
```

## Этап 11. Списки и коммит

1. Обновить списки зоны: `python3 scripts/generate_lists.py` (или вручную по алгоритму 11 — тогда честно указать `генератор: вручную`).
2. Коммит по §15a.2: `feat|fix|docs|refactor|verify|chore|backup(<область>): <описание>`; области: материалы, изделия, технологии, модели, реализации, стандарты, группы, произведения, алгоритмы, шаблоны, списки, ci.

## Анти-паттерны ИИ (12 типичных ошибок)

| # | Ошибка | Правильно |
|---|---|---|
| 1 | Выдуманное число «из памяти» | Веб-поиск/расчёт + источник; иначе `null` |
| 2 | `{min, max, nominal}` в свойствах (запрет v6) | Одно значение-номинал; границы — парой именованных полей; окно — в `допуски` |
| 3 | Дублирование чисел в теле | Числа — только в front matter (F26) |
| 4 | Свободный текст в enum-поле | Только значения из списка схемы |
| 5 | `---` внутри тела | Разделы — только заголовками `##` |
| 6 | Второй «основной» структурный вариант | Ровно один `основной: да` |
| 7 | Цена материала одна на все варианты | Цена — в `экономика` каждого варианта |
| 8 | Ссылка на несуществующую карточку | Сначала создать/проверить цель ссылки |
| 9 | Копирование свойств предка в обёртку | Обёртка = только дельта §12.7 |
| 10 | `TBD`/`varies per canon` как значение | `null` + обоснование |
| 11 | Изменение предка при создании обёртки | Предок остаётся `real` |
| 12 | Список «обновлю потом» | Списки — в том же коммите, что и карточки |

## Дисциплина null

`null` — допустимое «нет данных / не применимо», но:

- поле не удаляется без причины (опциональные поля не указываются вовсе; null — там, где отсутствие данных содержательно);
- для каждого значимого null — обоснование в теле карточки;
- для чисел: сначала попытка найти (веб-поиск/расчёт), потом null.

## Диапазоны и единицы (v6)

- Единицы — в суффиксе имени поля: `_МПа`, `_ГПа`, `_C`, `_кг_м3`, `_pct`, `_S_м`, `_вт_м_к` (у моделей — латиницей: `_kg`, `_mm`, `_W`, `_s`, `_GHz`, `_dB`).
- Свойство = одно значение (номинал зафиксированного варианта).
- Диапазоны разрешены ТОЛЬКО: пары именованных полей (`минимальная_рабочая_температура_C`/`максимальная_рабочая_температура_C`); блоки требований `{min, target}` (§12.4.1, маскировка, ТТХ — это спецификации); истинные рабочие интервалы (`диапазон_Гц {min, max}`).
- Даты — `ГГГГ-ММ-ДД`; габариты — `{l, w, h}` (три размера, не диапазон).
