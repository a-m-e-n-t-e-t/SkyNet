# Шаблоны карточек SkyNet Knowledge Engine

> Единая система шаблонов для создания карточек базы знаний SkyNet.
> Основано на YAML-схемах §12 промпта (SkyNet_PROMPT_v9.31+, «Промпт-как-код») и практике наполнения (сотни карточек в трёх доменах данных).
> Каждый шаблон самодостаточен: полная структура полей, правила заполнения и чек-лист встроены в файл.
>
> **Списки v2 (2026-11-27)** — 5 новых списков (стандарты, исследовательские группы, произведения, фантастические материалы, реализации), карточка-обёртка ии-улучшения (§12.7), сводный реестр v1.1 и инструменты `scripts/` — генератор и валидатор (см. «Историю исправлений»).
> **Карточки v10/v11** — единый блок `метаданные` во всех карточках (версия_схемы, реальность, доступность, статус, источник, создано/обновлено); материал v10.1: `структурные_варианты` с машиночитаемыми `id` и связью `вариант_id` в карточке изделия; стандарт/группа/произведение v11.0: `обозначение`/`статус_действия`, `специализация`, кросс-связи произведений.
> **Версия 6** — «одно свойство — одно значение»: конструкции `{min, max, nominal}` удалены из всех шаблонов (материал, технология, изделие, реализация); границы диапазона — парой именованных полей, окно процесса — в поле «допуски» (см. «История исправлений»).
> **Версия 5** — свойства стали вложенными в каждый вариант `кристаллическая_структура` (`существует` + сложные поля `основные`/`дополнительные` у каждого варианта), `химическая_стойкость` разбита на отдельные поля по средам, enum вариантов расширен до 14 (+ `микрокристаллический`) (см. «История исправлений»).
> **Версия 4** — `кристаллическая_структура` стала сложным полем (`основные` + `дополнительные`, с сингонией/структурным типом/текстурой); `оптимальная_структура` перенесена из карточки материала в карточку изделия как вложенное поле `материалы_частей` (см. «История исправлений»).
> **Версия 3** — устранено дублирование осей классификации модели: поле `класс` (дубль `тип_модели`) удалено, enum `тип_модели` канонизирован по §11.0, `категория` определена как семейство/серия (см. «История исправлений»).
> **Версия 2** — устранены две проблемы: дублирование данных (YAML + таблицы в теле) и «сливание» содержимого между `---` при рендере на GitHub (см. «Правила структуры файла»).

## Правила структуры файла (рендер на GitHub)

1. **Строка 1 файла — всегда `---`.** GitHub распознаёт YAML front matter только если открывающий `---` стоит в первой строке; тогда блок выводится отдельной таблицей вверху страницы. Если перед `---` есть любой текст (HTML-комментарий, инструкция) — front matter не распознаётся, и всё содержимое между `---` «сливается» в единый текст с телом карточки.
2. **Служебные комментарии шаблона** (инструкции по размещению) находятся ПОСЛЕ закрывающего `---`, в HTML-комментарии `<!-- ... -->`: в рендере они невидимы, а front matter остаётся распознанным.
3. **Внутри Markdown-тела разделитель `---` не используется** (иначе он превращается в горизонтальную линию и «склеивает» соседние разделы): разделы разделяются только заголовками `##`.
4. **Одно значение — одно место (анти-дублирование, F26).** Все числовые и enum-значения вносятся ОДИН раз — в YAML front matter; GitHub отрендерит их таблицей в начале страницы. Markdown-тело — повествование, ссылки, методики и чек-листы; значения из front matter в теле не повторяются. Это исключает расхождение копий данных и двойной ввод.

## Правила сводных списков (`_*.md`)

1. **Список = только навигация и классификация.** Запись списка — `id — Название → путь` (для моделей — строка таблицы с классификацией; для частей — уровень иерархии). Числовые свойства, TLR, доли массы и цены в списках ЗАПРЕЩЕНЫ: «одно значение — одно место» (F26) — источник всегда карточка.
2. **Метаданные списка** — в front matter (строка 1 = `---`): `тип_файла: список`, `генератор`, `охват`, `домен`, `обновлено`, `счётчики`. Счётчики машиночитаемы: CI сверяет сумму секций с `всего` и число карточек в зоне с числом записей списка.
3. **Полнота секций.** Все группы классификационного enum присутствуют ВСЕГДА, включая пустые «(0)» со строкой «- — нет —»: пустая группа — факт трекинга полноты (например, подсистема без изделий), а не ошибка списка.
4. **Группировка и сортировка.** Группировка — по enum карточки (класс материала / подсистема §11.0 / категория технологии / тип модели §11.0 / категория произведения §9 / категория стандарта); без enum — единая секция (группы §10.2, фантастические материалы §12.3a: урок v3 — классификация живёт в схеме, не в списке); сортировка — по алфавиту id внутри секции (произведения — по номеру work_NNN); реализации — секция на модель × 3 типа реализаций.
5. **Имена и зеркала.** Сводный файл начинается с `_` (§15a.1); на домен — один список каждого типа; в `работа и и/` попадают только карточки `<оригинал>__ии.md`.
6. **Актуальность.** Список обновляется в том же коммите, что и карточки зоны (генератор `scripts/generate_lists.py` либо вручную; поле `генератор` указывается честно). Отставание списка от карточек зоны — диагностируемая метрика CI (`--check`), а не молчаливый долг.

## Правила обёрток ии-улучшения (§12.7, домен `работа и и/`)

1. **Обёртка = дельта.** Свойства предка в обёртку НЕ копируются (F26): обёртка хранит только `предок` + `улучшения` + `real_check`; свойства читаются из карточки предка.
2. **Размещение и имена.** `работа и и/материалы/<оригинал>__ии.md`, `работа и и/технологии/<оригинал>__ии.md`; обёртки-изделия (верхний уровень и части) — `работа и и/изделия/<подсистема>/<оригинал>__ии/_index.md`. id обёртки = `<id предка>__ii` (латиница, KEBAB-CASE).
3. **Статусы.** `метаданные.версия: ии-улучшенная`, `статус_реальности: ии-улучшенная`, `ии_перепроектирован: да`; карточка предка не изменяется (предок остаётся `real`).
4. **Служебные обёртки моделей** (вариант D v9.40, `izdelie_SkyNet-<имя>`, `scripts/generate_wrapper_izdeliya.py`) — полные карточки для поддержки декомпозиции, НЕ дельты §12.7; шаблоном №10 не покрываются.
5. Зеркала списков `работа и и/<тип>/` обновляются в том же коммите, что и обёртки.

## Инструменты (scripts/)

- `scripts/generate_lists.py` — генератор и сверщик сводных списков: обходит домены базы знаний, читает front matter карточек и обновляет 11 `_список_*.md` (+ зеркала) и `_сводный_реестр.md` по правилам шаблонов №11–21; режим `--check` — CI-сверка списков с карточками (код выхода 1 при расхождении). Поддерживает миграцию старых списков v0 (класс → тип_модели по v3; секции нового формата) и диагностику: ссылки на стандарты без карточек, модели вне канонических типов §11.0. Поле `генератор` в списках должно быть честным.
- `scripts/validate_templates.py` — валидатор папки `шаблоны/` (21 шаблон + README): структура файла (`---` первой строкой, без `---` в теле), парсинг YAML front matter, единый блок `метаданные`, правила v3–v6, обёртка §12.7, метаданные и полнота секций списков. Пути — относительно скрипта, работает из любого клона; карточки базы знаний (не шаблоны) проверяет `pre-commit-hook.py` развёрнутой базы.

## Как использовать шаблон (5 шагов)

1. **Скопируйте** шаблон в целевую папку (см. таблицу выше).
2. **Переименуйте** по конвенции §15a.1: только строчные буквы, пробелы → `_`, длина 3–80, без `/\ : * ? " < > |`; сводный файл начинается с `_`.
3. **Заполните YAML front matter** (между `---` и `---`): замените все `<...>`; поля с пометкой `# →` обязательны. Это — ЕДИНЫЙ источник данных карточки; сохраняйте `---` первой строкой файла.
4. **Заполните Markdown-разделы** после закрывающего `---`: только повествование (описание, принцип работы, анализ, аналоги, источники, чек-лист). Числа из front matter в теле не дублируются; разделы разделяются заголовками `##`, а не `---`.
5. **Проверьте и закоммитьте**: шаблоны — `python3 scripts/validate_templates.py`; списки зоны — `python3 scripts/generate_lists.py`; карточки развёрнутой базы — `scripts/pre-commit-hook.py`; коммит по §15a.2 (`feat(материалы): ...`).

## Условные обозначения во всех шаблонах

- `<...>` — плейсхолдер: заменить реальным значением и удалить угловые скобки.
- `null` — допустимое «нет данных / не применимо» (обоснованный null; не удалять поле без причины).
- `# →` — поле обязательно (указана метрика F-…, которая его контролирует).
- `# (опц.)` — поле опциональное.
- TODO-подобных маркеров в финальной карточке быть не должно (§24.2).

## Общие правила для всех карточек (§12.0, §0.2, §22, §24, §32)

1. **Административный блок §12.0** (обязателен во всех схемах): `источник_разбора`, `ии_перепроектирован`, `дата_создания`, `дата_обновления`.
2. **Enum-значения** — только из допустимых списков схемы (§0.2 enum validation); недопустимое значение = блокировка.
3. **Прозрачность источников (§22)**: у каждого числа — источник (`источник`, `источник_url`, `источник_дата`); «phantom»-значения без источника запрещены.
4. **Заполненность (§24)**: 100% полей без placeholder'ов; `TBD/FIXME/XXX/"varies per canon"` запрещены.
5. **TRL-шкала доступности (§32)**: `фантастический | теоретический | лабораторный | ограниченный | промышленный | ии_проект | устаревший`.
6. **Статусы реальности**: в `реальные данные/` — только `real`; в `фантастические данные/` — `canon` или `canon_realizable`; `работа и и/` — `ии-улучшенная`.
7. **Даты** — формат `ГГГГ-ММ-ДД`. **Ссылки** — относительные Markdown-пути (§15a.3).
8. **Одно свойство — одно значение (v6).** Числовое свойство в front matter — одно число (номинал/типичное для зафиксированного варианта: варианта структуры материала, режима технологии, конкретного изделия). Конструкция `{min, max, nominal}` не используется. Границы диапазона — парой именованных полей (`минимальная_рабочая_температура_C` / `максимальная_рабочая_температура_C`); окно процесса — в поле `допуски`; разброс от термообработки — в `варианты_по_применению.свойства` или карточке технологии. Спецификация в карточке модели — пара `min`/`target` (требование «не хуже min, цель target»), это не свойство.

## Чек-лист готовности карточки (перед коммитом)

- [ ] Файл начинается со строки `---` (front matter распознан); внутри тела нет разделителей `---`.
- [ ] Все `<...>`-плейсхолдеры заменены; маркеров `TODO/TBD/FIXME` нет.
- [ ] `id` уникален и в KEBAB-CASE с префиксом сущности (`material_`, `izdelie_`, `tekhnologia_`, `SkyNet-`, `standart_`, `group_`, `SkyNet-Work-`).
- [ ] Обязательные поля схем (помечены `# →`) заполнены; enum-значения из списков.
- [ ] Числа имеют источники; null-поля обоснованы в тексте.
- [ ] Данные не дублируются: числа/enum-значения — только в front matter; тело — повествование, ссылки и чек-листы.
- [ ] Внутренние ссылки — относительные и не битые.
- [ ] Коммит-сообщение по §15a.2: `feat|fix|docs|refactor|verify|chore|backup(<область>): <описание>`.

- **Списки v1 (2026-11-27)** — добавлена система шаблонов списков (6 файлов, №9–14): материалы (8 классов enum §12.3), изделия (13 подсистем §11.0 + прочее), части/ведомость (уровни 2–4, §12.6), технологии (5 категорий enum §12.2), модели (7 типов §11.0; колонка `класс` удалена по правилу v3, добавлена `обёртка_ии` по варианту D), сводный реестр (счётчики доменов × типы + покрытие списками). Правила: список — только навигация (F26); front matter с машиночитаемыми счётчиками для CI; полнота секций enum (пустые «(0)» не удаляются); сортировка по алфавиту id; обновление в том же коммите, что и карточки.
- **v6** — «одно свойство — одно значение» (материал + технология + изделие + реализация):
  1. Конструкции `{min: null, max: null, nominal: null}` удалены: `прочность_МПа`, `предел_текучести_МПа`, `усталостная_прочность_МПа` (свойства варианта кристаллической_структуры — номиналы; разброс от термообработки — в `варианты_по_применению`/карточке технологии), `температура_режима_C`, `давление_Pa`, `время_цикла_s`, `кпд_процента`, `производительность_шт_ч` (номиналы режима; окно — в `допуски`), `масса_kg`, `выработка_энергии_W`, `выработка_тепла_W` (изделие и реализация — конкретный объект: одна масса, номинальные выработка/тепло; `наследуемые` суммируют скаляры дочерних).
  2. Без изменений: `габариты_mm {l, w, h}` — три разных размера, не диапазон; `{min, target}` в спецификации карточки модели — требования («не хуже min, цель target»), не свойства; `диапазон_Гц {min, max}` — истинный рабочий интервал; `{computed_from}` — вычислимые агрегаты.
  3. Валидатор расширен проверками v6 (рекурсивный запрет конструкции `{min, max, nominal}` во всех шаблонах).
- **v5** — свойства — в каждый вариант кристаллической_структуры (`шаблон_материала.md` + `шаблон_изделия.md`):
  1. `кристаллическая_структура` — СЛОЖНОЕ поле-список: у КАЖДОГО варианта — `существует` (да/нет; при «да» заполняются свойства) и вложенные сложные поля `основные` (кристаллография — сингония, структурный_тип, пространственная_группа + базовые физ.-мех.: плотность, прочность, текучесть, модуль, Пуассон, плавление, теплофизика, цена) и `дополнительные` (по применению: роль, текстура, вязкость, усталость, электропроводность, твёрдости, магнитность, демпфирование, пористость, рабочие температуры, `химическая_стойкость`). Ранее свойства жили на верхнем уровне и относились только к первому «основному» варианту — теперь каждый вариант несёт собственные свойства (α- и β-фазы титана, моно- и поликристаллы различаются по всем параметрам); верхнеуровневые блоки свойств удалены как дублирование.
  2. Единое текстовое поле «Химическая стойкость» (раньше — строка в теле карточки) разбито на отдельные поля по средам: `вода_и_влажность`, `кислоты`, `щёлочи`, `солевой_туман`, `растворители_и_топливо`, `высокотемпературное_окисление`, `УФ_излучение`, `радиация`, `биоповреждения` (enum `высокая|средняя|низкая|нестойкий|н_д`) + `скорость_коррозии_мм_год` (число) — в `дополнительные` каждого варианта.
  3. Enum «вариант» расширен до 14 значений: + `микрокристаллический` (зерно 0.1–10 мкм — заполнен пробел между поли- и нанокристаллическим).
  4. Новые свойства вариантов: `минимальная_рабочая_температура_C`, `максимальная_рабочая_температура_C`, `пористость_процентов`; в исходном фрагменте-предложении поле `минимальная_рабочая_температура` дублировалось — вторая копия исправлена в `максимальная_рабочая_температура` (правило уникальности имён полей).
  5. `шаблон_изделия.md`: enum `оптимальная_структура.структура` синхронизирован с материалом (добавлены `микрокристаллический`, `молекулярный_кристалл` — раньше отсутствовал). Валидатор расширен проверками v5.
- **v4** — кристаллическая структура и оптимальная структура (`шаблон_материала.md` + `шаблон_изделия.md`):
  1. `кристаллическая_структура` — СЛОЖНОЕ поле: `основные` (≥1 основной вариант: `вариант` + `сингония` + `структурный_тип` + `пространственная_группа` + `текстура`) и `дополнительные` (полиморфы, вторые фазы, компоненты композита — с полем `роль`). Обоснование: анализ 202 карточек материалов показал, что enum из 4 значений не покрывал практику — значение `полукристаллический` (полимеры) отсутствовало, ~40% полей заполнялись свободным текстом с сингонией, структурным типом, пространственной группой, фазами и текстурой. Enum `вариант` расширен до 13 значений: + `полукристаллический`, `нанокристаллический`, `стеклокерамика`, `квазикристаллический`, `жидкокристаллический`, `жидкость`, `газ`, `молекулярный_кристалл` (было: моно-, поли-, аморфный, композиционный, н_д).
  2. `вариант_структуры` (single_phase|two_phase|multiphase) удалён как дубль: число фаз выводится из состава `кристаллическая_структура` (основные + дополнительные); в практике поле выродилось в 90+ произвольных текстовых значений.
  3. `оптимальная_структура` перенесена из карточки материала в карточку ИЗДЕЛИЯ как вложенное поле `материалы_частей` (F62/P062): оптимальная структура определяется применением (частью/узлом), а не самим материалом. В карточке материала остаётся «меню» вариантов: `кристаллическая_структура`, `варианты_по_применению`, `сравнение_структур`. Поле `применение_по_умолчанию` удалено как дубль контекста части. F62 проверяется в B-BOM изделия; 73 карточки изделий архива уже содержали `оптимальная_структура` — шаблон узаконил фактическую практику. Валидатор расширен проверками v4.
- **v3** — дедупликация классификации модели (`шаблон_модели.md`): удалено поле `класс` — анализ 41 карточки архива показал, что в 95% случаев оно совпадало с `тип_модели` (полная копия; P074 сам называет 7 типов §11.0 «классами»), а его enum из §12.4 (`терминатор|аэробот|…`) в реальных карточках никогда не использовался. Теперь `тип_модели` — единственная ось физического типа с каноническим enum §11.0 (`стационарный` вместо неканонического `ИИ-ядро` — последнее является значением `категория`); `категория` переопределена как вторая, НЕ дублирующая ось «семейство/серия» с enum по реальной практике архива (`стандартный`, `жидкий_металл`, `ранняя_наземная`, `воздушный_HK`, `наземный_HK`, `водный_HK`, `ИИ-ядро`, `гибрид`, `альтернативный_производитель`, `GRACE`, `прочее`). Старые карточки со `класс` совместимы: их `класс` читается как `тип_модели`.
- **v2** — анти-дублирование: удалены таблицы характеристик в Markdown-теле, дублирующие поля YAML front matter; введено правило «одно значение — одно место» (front matter = единственный источник данных). Рендер: `---` — первая строка каждого шаблона (front matter распознаётся GitHub и выводится таблицей), служебные комментарии перенесены после закрывающего `---`, внутри тела `---` не используется. Инструкции README синхронизированы.
